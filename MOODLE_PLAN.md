# Moodle — implementation plan

Version 2, written 2026-09-19. Replaces the plan of the same morning.

This is a plan. Nothing in it has been built. Every technical claim was verified
against Moodle's own source on branch `MOODLE_405_STABLE` (with spot checks on
3.9, 4.1, 4.4, 5.0 and 5.2) and against the Semora repository at commit
`8cea350`, then independently attacked by three skeptics per claim. Where a
claim was refuted, this document carries the correction, not the claim.

**The owner's requirement, verbatim:** "Moodle should be easy to implement and
should update all the class information as much as it can like canvas … an
excellent/strong foundation for semora."

---

## 0. Read this first

### The route recommended on 2026-09-18 is closed, and this is why

The previous version of this plan, and the message that preceded it, recommended
Moodle's browser sign-in hand-off (`admin/tool/mobile/launch.php`) as the
primary road because it yields a full web-service token. Three independent
skeptics refuted it, all reading the source. Two facts close it on any default
Moodle site:

1. **`tool_mobile/forcedurlscheme` defaults to `'moodlemobile'`** since Moodle
   3.8 (MDL-66501, commit `d4985a7`, September 2019). `launch.php` replaces
   whatever scheme a third-party app asks for with that value (lines 118-124),
   so the token is delivered to the official Moodle app's scheme, never to
   `semora://`. The setting is not exposed by the public config, so it cannot be
   detected in advance.
2. **`tool_mobile/typeoflogin` defaults to 1, "via the app"**, and with that
   value `launch.php` throws `pluginnotenabledorconfigured` before the login
   page is even shown (lines 70-76), unless OAuth2 auth is enabled or the
   student happens to have logged in on the immediately preceding request.

It also can never deliver a token to `app.semoraai.com`, because it redirects
only to a URL scheme. The full spec for that road is parked in §12 with the
exact condition under which it becomes worth building.

### The calendar link is the road, and every competitor agrees

Shovel, DormWay, Coursicle and SyllabusAI all integrate Moodle the same way:
the student copies the calendar export URL Moodle prints and pastes it. Nobody
in the market has anything richer for Moodle. Motion, Sunsama, iStudiez,
Studley, Todoist, Notion and TickTick have no Moodle integration at all. The
official Moodle app is the only richer client, and the mechanism it uses is the
one closed to third parties above.

### What this plan delivers, honestly

| | Canvas today | Moodle after this plan |
|---|---|---|
| student self-serves, no admin | yes | yes |
| works through university single sign-on | yes | yes, fully |
| every enrolled course | only those with dated work | only those with dated work — identical |
| deadline updates in the background | 1h / 3h / 24h | same cadence, inherited |
| overrides the instructor set for the student | n/a | yes |
| extensions the instructor granted | n/a | yes — corrected 2026-09-19, see §1.6 |
| points and grades | none | none |
| link back into the platform | per item | to the calendar day only |
| course identity | numeric id | shortname text |
| survives a password change | yes | **no** — the link dies; SSO users are exempt |
| horizon | whole term | one year on a default site, never less than 60 days |
| web app (`app.semoraai.com`) | yes | yes |

The one thing the owner asked for that a calendar feed cannot give is a course
with no dated work. Canvas has exactly the same limit today, and all 57 live
Canvas connections accept it.

## 1. How Moodle actually works

Every line reference is to `MOODLE_405_STABLE`.

### 1.1 The student's route

**Calendar → Import or export calendars → Export calendar → Get calendar URL →
Copy URL.** The page is `calendar/export.php`; pressing Get calendar URL (the
`generateurl` branch, lines 162-175) prints:

```
https://<wwwroot>/calendar/export_execute.php
    ?userid=<id>&authtoken=<sha1>&preset_what=<what>&preset_time=<time>
```

All four parameters are always present on a link generated by that page.
`<wwwroot>` may include a path: a school installed under
`https://school.edu/moodle` prints exactly that.

The page also has a plain **Export** button that downloads `icalexport.ics`. On
iPhone that opens a calendar-subscription preview, and a student who takes that
path comes back with nothing to paste. The connect flow must handle this (§7,
Phase 4).

### 1.2 The token

```php
function calendar_get_export_token(stdClass $user): string {
    return sha1($user->id . $DB->get_field('user', 'password', ['id' => $user->id])
                . $CFG->calendar_exportsalt);
}
```
`calendar/lib.php:4016`. On Moodle 3.9 the function does not exist but the
identical sha1 is inline (`calendar/lib.php:3720`).

Consequences, each verified:

- It is a **bearer credential**. Anyone holding the URL reads that student's
  calendar. Treated exactly as the Canvas feed URL: Vault only, never a device
  copy, never logged, never in an error string, never in analytics.
- It **does not sign the query string.** `preset_what` and `preset_time` can be
  rewritten on a pasted link and it still authenticates. This is what lets
  Semora fix a student who chose "This week".
- It **dies when the password hash changes.** Usually a password change. Also
  a silent rehash on the next login after a site upgrades its hashing. **SSO
  users carry the constant `not cached` as their password field, so their link
  never dies on a password change** — only on a salt rotation.
- `export_execute.php` runs with `NO_MOODLE_COOKIES` (line 27): no session, no
  capability check, token only.

### 1.3 The date window

`preset_time` accepts `weeknow | weeknext | monthnow | monthnext |
recentupcoming | custom` (`export_execute.php:73`).

| preset | window | where |
|---|---|---|
| absent | `weeknow` — **this week only** | line 67 |
| `recentupcoming` | last 5 days, next 60 | lines 200-204 |
| `custom` | `calendar_exportlookback` … `calendar_exportlookahead` | lines 205-209 |

`calendar_exportlookahead` defaults to **365** and `calendar_exportlookback` to
**5** (`admin/settings/appearance.php:117-118`; admin choices for look-ahead are
365/180/150/120/90/60/30/5). `export_execute.php` never checks
`calendar_customexport`, so `custom` works even when the UI hides it.

So on a default site `preset_time=custom` returns a full academic year. Because
an administrator can narrow it, the fetcher also asks for `recentupcoming` when
the custom horizon comes back under 60 days, and unions the two by UID. The
student never gets fewer items than the best preset would give, and never less
than 60 days.

### 1.4 What is in the feed

`preset_what=courses` → events of the student's **active** enrolments only
(`enrol_get_users_courses($user->id, true)`, line 91). `preset_what=all` adds
the student's personal events, group events, category events, and site events
under a **synthetic pseudo-course whose shortname is the localised string
`calendar/siteevents`** (lines 106-110).

Each `VEVENT` (lines 236-273):

| property | value |
|---|---|
| `UID` | `<event id>@<wwwroot minus scheme>` — a sub-directory install yields `123@school.edu/moodle` |
| `SUMMARY` | the event name — written in **the creating teacher's language** at save time, not the student's |
| `DESCRIPTION` | plain text, HTML stripped |
| `CLASS` | `PUBLIC` |
| `LAST-MODIFIED` | `timemodified` |
| `DTSTAMP` | now |
| `DTSTART` / `DTEND` | UTC `Z`; equal for a due instant (duration 0, lines 262-264) |
| `LOCATION` | optional |
| `CATEGORIES` | **course shortname**, only when `courseid != 0` |

**There is no `URL` property.** Moodle never emits one. There is no
`modulename`, `eventtype`, `cmid` or numeric course id either.

Activities the student cannot see (restricted access, hidden course) are
skipped (`uservisible`, lines 227-230). A course hidden from students is
therefore absent from the feed even if its deadlines are set. Undated
assignments produce no event.

Moodle imposes no event cap (`$limitnum = 0`, line 130); Semora's 5 MB body cap
is the only ceiling. The body is served with `Content-Disposition: attachment;
filename=icalexport.ics`.

### 1.5 What a failure looks like

`export_execute.php` **never emits 401/403/404**. A bad token, a deleted user
and disabled export all `die()` with **HTTP 200 and a plain-text body served as
`text/html`**: `Invalid authentication` (lines 48-56) or `no export` (lines
38-39, when `enablecalendarexport` is off). Every 4xx therefore comes from
infrastructure — a WAF challenge, an SSO gateway, maintenance — never from
Moodle rejecting the token. Classification must key on the body text and
never on the status code or content type. Getting this wrong purges a
student's credential for a transient block.

### 1.6 Overrides and extensions

Verified in `calendar/classes/local/event/strategies/raw_event_retrieval_strategy.php`
lines 246-264 and `export_execute.php` lines 87-118:

- Under `preset_what=courses` the filter is `(e.groupid = 0 AND e.courseid IN
  …)`: the **base** event appears with the base date; no override does.
- Under `preset_what=all`, a **user override** (courseid 0, userid = student,
  priority 0) and a **group override** (courseid = course, groupid ≠ 0) join the
  union, and a `MIN(priority)` subquery suppresses the base event.

So a base UID present under `courses` but absent under `all` means the student
holds an override, and the override's `DTSTART` is the student's real date. The
user override has no `CATEGORIES`; the group override has the course's. Override
event names follow `'{name} - Override'` / `'{name} - {group}'` with a
`(Due date)` parenthetical (`mod/assign/lib.php:288-326`,
`mod/quiz/lib.php:1312-1356`).

**Extensions DO produce an event — corrected 2026-09-19.** The first version of
this plan, and the verification pass behind it, both said Grant extension
creates no calendar event. Read live from `mod/assign/locallib.php:7034-7062`,
it does:

```php
$event->name      = get_string('calendarextension', 'assign', $instance->name);
$event->courseid  = 0;        // -> no CATEGORIES
$event->userid    = $userid;  // -> a user event: preset_what=all only
$event->priority  = null;     // -> does NOT suppress the base
```

English `calendarextension` is `{$a} is due (extension)`, Spanish
`{$a} ha vencido (extension)`. Because its priority is NULL and the base's is
too, **both survive** the MIN(priority) join, unlike an override where the base
disappears. So there are THREE date sources, not two, and a parser that drops
every event without CATEGORIES would throw the student's real date away.

### 1.7 Suffixes on event names

Moodle builds event names as `'{name} is due'`, `'{name} is due to be graded'`,
`'{name} opens'`, `'{name} closes'`, `'{name} opens for submissions'`,
`'{name} deadline for submissions'`, `'{name} opens for assessment'`,
`'{name} deadline for assessment'`, `'{name} should be completed'` — in the
language of the teacher who saved the activity. The parser strips them by a
table generated from language packs, not hand-copied (§7, Phase 0.4).

Before Moodle 3.3 (MDL-58082, ~10 % of registered sites are ≤3.11) a quiz has
**one** event with `DTSTART` = open and `DTEND` = close and no suffix. The
parser needs a rule for that shape or those quizzes import at their opening
time.

### 1.8 The public probe

`tool_mobile_get_public_config` is declared `loginrequired => false`
(`admin/tool/mobile/db/services.php:38-46`) and is callable with no token at
`<wwwroot>/lib/ajax/service-nologin.php?args=[{"index":0,"methodname":"tool_mobile_get_public_config","args":{}}]`.
It returns `wwwroot`, `sitename`, `enablewebservices`,
`enablemobilewebservice`, `typeoflogin`, `launchurl`, `identityproviders`,
`maintenanceenabled` (`admin/tool/mobile/classes/external.php:138-198`). It does
**not** return `forcedurlscheme`. Tested on `clase.moodlecloud.com` on
2026-09-19: **403 for the user agent `Semora-Moodle-Calendar/1.0`, 200 for a
Safari user agent**, while `export_execute.php` answered both. The probe's
user-agent policy is an owner decision (§11).

### 1.9 Version spread

From stats.moodle.org on 2026-09-19, 146,922 registered sites: 4.5 = 24.2 %,
5.2 = 21.6 %, 5.0 = 7.9 %, 4.1 = 7.7 %, 5.1 = 6.9 %; 16.8 % on ≤3.11; 10.3 % on
<3.10. Higher education skews newer. The calendar export exists since Moodle
1.9 and the `userid+authtoken` form since MDL-27542, so the road works on
every version in the wild. Minimums for the parked road: `launch.php` 3.2,
`oauthsso` 3.3, `core_calendar_get_calendar_export_token` 3.10.

## 3. The one thing a calendar feed cannot do

A calendar feed contains events. Courses are inferred from them. A course with
no dated item inside the window does not appear. **Canvas works exactly the
same way today** (`canvas-calendar.ts:288`).

So "all of their courses" means, precisely: every course that has at least one
dated item inside the window. Two further cases the copy must name:

- A course the teacher has **not released to students yet** is absent even if
  its deadlines are set.
- A course with **only undated** assignments never appears.

The kept web-service token lane (`core_enrol_get_users_courses`) lists every
enrolment including empty ones, which is why it stays as a second door.

## 4. The shape of the answer

| road | who | how reached |
|---|---|---|
| **Calendar link** — new, the default | every student, every school | the connect screen |
| **Web-service token** — exists, hardened | schools whose IT issues one | "My school gave me a web-service token" |
| **Browser sign-in** (`launch.php`) — parked | nobody, on a default site | §12, do not build |

The student never chooses a road. They give their school's Moodle address and
paste one link.

**The identity invariant**, named here so nothing ever duplicates a task:
`external_id` = the feed UID verbatim (`<eventid>@<host>`),
`external_course_id` = the shortname verbatim. Any future token lane must emit
the same keys — the calendar event id and the course shortname — so a feed
connection upgrades in place.

## 5. The student journey

1. **Settings → Canvas or LMS Sync.** The Moodle row reads *"Deadlines, quizzes
   and exams from your Moodle calendar — no admin needed."* Tapping it fires
   `lms_provider_tapped` and opens *Connect Moodle · MOODLE SETUP · STEP 1 OF 2*.

2. **"Where is your Moodle?"** One field. They type a host, or paste any Moodle
   page they have open, and Semora recovers the site root. Below the field: *If
   you are not sure, search "moodle" and your school's name.* If a school
   picker exists (seeded from real connections after launch) they pick instead.
   Tap **Find my Moodle**.

3. **"Checking that address…"** runs the server's no-login probe against the
   typed origin and bounded guesses: `moodle.<host>`, `lms.<host>`,
   `<host>/moodle`. Result: *Found: University of X Moodle* with *Not your
   school? Change* — or *Couldn't confirm this address — continue anyway*. It
   **never blocks**. Site, site name, lane and attempt count — never the link —
   are saved under a Moodle-specific device key the moment they exist, so
   leaving the app never restarts from step 2.

4. **"Phone or laptop?"** Phone: a card *Open your Moodle calendar* with
   *1. Sign in if Moodle asks. 2. Tap Get calendar URL. 3. Tap Copy URL.
   4. Come back to Semora.* and *Leave the options as they are — Semora sets the
   date range itself.* Two more lines: *If the page just says "no export", your
   school turned this off — tap Scan a syllabus instead.* and *If you tapped
   Export and a calendar file opened, go back and tap Get calendar URL
   instead.* The button *Open moodle.yourschool.edu* opens
   `<wwwroot>/calendar/export.php` in the in-app browser sheet. **On iPhone the
   sheet does not share Safari's session** (SFSafariViewController keeps its
   own store since iOS 11), so expect a full SSO and MFA login inside it the
   first time. The card says when to choose the laptop lane instead: *If your
   school's sign-in refuses to open here, use the laptop steps.* Laptop: the
   same four taps written for a laptop, then *open Semora on your phone or
   app.semoraai.com and paste it.* Both lanes also carry the manual route for
   when SSO lands on the dashboard instead of the export page: *Calendar →
   Import or export calendars → Export calendar.*

5. **In Moodle** they tap Get calendar URL then Copy URL. Nothing to choose.
   Because the school's Moodle may be in a different language from the
   student's Semora, the card shows the button label in both languages where
   they differ.

6. **Back in Semora** the card collapses to *Back already? Paste your link*
   with a *Paste from clipboard* button — never an automatic read. The masked
   field shows a live verdict and auto-advances after 450 ms. A wrong paste is
   named while they look at it: *That's the Moodle sign-in page.* / *That's the
   Export page — tap Get calendar URL, then Copy URL.* / *That's a downloaded
   file, not the link.* / *That link is from a different Moodle than the one
   you chose.* — each with *Open it again*. Two failed discoveries escalate to
   the laptop lane and *Send us a note*.

7. **The server** canonicalises the link (only `userid` + `authtoken` kept),
   fetches `courses/custom` and `all/custom`, adds the `recentupcoming` pair
   only if the horizon is under 60 days, and STEP 2 OF 2 *Choose courses* shows
   what a Canvas student sees: *5 courses · 62 deadlines · Sep 2 – Dec 18*, every
   course pre-ticked with its own count and span, semester auto-matched or
   proposed inline. Course names are Moodle's shortnames with *Tap a name to
   change it*. One honest line: *Only classes with dated work in Moodle appear
   here. A class with nothing scheduled, or one your teacher hasn't released
   yet, shows up when its first deadline is posted.* If narrowed: *Your Moodle
   shares 30 days ahead.*

8. **Import and sync** → *Moodle connected — 5 courses and 62 deadlines
   imported. Semora will keep checking Moodle every few hours.* → *See my
   deadlines*. The link went straight to the Vault; nothing on the phone.

9. **Nothing dated yet** (early term): instead of a refusal, *Your Moodle
   calendar has no due dates right now. Semora saved your link and checks every
   few hours; courses appear as soon as an instructor adds a date — or as soon
   as your teacher makes the course visible.* with *Save and keep checking*.
   The connection exists with zero courses.

10. **From then on** it behaves like Canvas: hourly while active in term, every
    three hours otherwise, daily when dormant. A moved due date moves. An
    override the instructor set for them personally shows their own date, **and
    so does an extension they were granted.** A new item appears. A deleted item disappears
    inside the window the feed vouched for. *Open in Moodle* opens the calendar
    day view. Next term, *Moodle is listing 3 new courses.*

11. **When the link dies** the card reads *Your Moodle calendar link stopped
    working — usually after a Moodle password change. Reconnect with a fresh
    link.* Reconnect reopens step 4 with the site prefilled. Tasks, edits and
    completions untouched. For a student whose school uses single sign-on, the
    link normally survives a password change and the card need not alarm them.

12. **On app.semoraai.com** the same screens render; *Open* opens a new tab and
    the student pastes. The rare student with a school-issued token taps *My
    school gave me a web-service token*. A Spanish account sees every string in
    Spanish.

## 6. Owner decisions

These change the work. Each is referenced from the step it gates.

1. **User-agent policy for the probe and the fetch** (gates 1.6, 1.7).
   MoodleCloud answers the probe 403 to a non-browser UA and 200 to Safari.
   Send a browser-like UA, or keep the honest `Semora-Moodle-Calendar/1.0` and
   accept "couldn't confirm" at every MoodleCloud school. This is a stance on
   how Semora identifies itself to schools.
2. **Keep or drop the token side door** (gates 2.7, 4.5). Zero token
   connections have ever existed. Keeping it creates the token→feed switching
   path that needs the in-place re-key in 3.5. Dropping it deletes the only
   way to list a course with no dated work.
3. **Turn removals on for Moodle** (gates Phase 3). The sweep is automated
   deletion of students' untouched rows on the strength of a parser. An
   explicit yes for Moodle removals, and for the −4/+horizon window, before 3.1.
4. **Free promo scope** (gates 4.5). Moodle rides `canvas_free`
   (`lms_access_allowed` is per account). Confirm Moodle is inside the offer,
   whether a zero-course "Nothing dated yet" save should stamp
   `free_promo_claimed_at`, and whether a Moodle-only student should ever see
   the Canvas-worded paywall.
5. **Which account runs the production smoke test** (gates 2.11) and an
   explicit yes for the rows it creates.
6. **Rename handling** (gates 3.5). Approve the re-key migration, or accept
   documented duplicates.
7. **Duplicate-connection guard scope** (gates 4.5). It changes the chooser
   for Canvas too. Moodle-only, or shared.
8. **Site events and group events** (gates 1.5). Drop site-wide events (many
   schools post exam periods there), and import unmatched group events as
   tasks — both are product calls.
9. **Ship vehicle if the fingerprint cannot be matched** (gates 6.2). Riding
   the next binary means an App Store submission with the deferred ASO
   checklist.
10. **Spanish card wording** when the school's Moodle is in another language:
    both labels, or neutral wording.
11. **Pricing-adjacent copy** in 7.2, migration 154, and the migration 153 push
    text — each needs its own line-by-line yes.
12. **Golden fixture provenance** (gates 1.1): the owner's own Canvas feed, or
    a synthesised one. Never a student's Vault credential.
13. **Politeness ceiling** (gates 1.6): how many requests per sync Semora may
    put on a university's Moodle. A WAF rate-limit lands on the student.

## 7. Phases

Every phase is shippable alone and leaves the app working. Phases 0-3 are
server-side and invisible. Effort is one engineer; elapsed is longer because of
the Phase 2 soak and OTA delivery.

| phase | what | effort | ships as |
|---|---|---|---|
| 0 | ground truth: a Moodle you control, fixtures, the ship vehicle | 2 days | nothing |
| 1 | a Moodle feed module beside the Canvas code, Canvas frozen | 2.5 days | nothing |
| 2 | wire it into sync, probe, timezone, token hardening | 2 days + 1 week soak | function + migration |
| 3 | windowed removal reconciliation | 1.5 days | function + migration |

**1.4 Validator rules.** Trim; take the first URL token out of surrounding
text; `webcal://` → `https://`; scheme-less → `https://`; `new URL()`; require
https, no credentials in the URL, port empty or 443; reject dotted-IP or
bracketed hosts; `blockedHost`; ≤4096 chars; pathname must **end with**
`/calendar/export_execute.php` (any prefix); query must carry `authtoken`
matching `^[0-9a-f]{40}$` and either `userid ^\d{1,12}$` or the legacy
`username`; **drop every other parameter**; clear the hash; return the
canonical string. Refusal messages never contain the input and are
byte-identical to the client strings in 4.1. The distinct wrong-paste shapes:
path contains `/login/` → sign-in page; path ends `/calendar/export.php` →
export page; `icalexport.ics` → downloaded file; different origin from the
chosen wwwroot → other host.

**1.5 Parser rules.**
- Both bodies must contain `BEGIN`/`END:VCALENDAR`.
- Walk `VEVENT`s with the shared loop; skip `STATUS:CANCELLED`; require
  `SUMMARY`, `UID`, `DTSTART`. **Do not require `URL`.**
- **Identity from the `courses` feed:** course key = decoded `CATEGORIES`
  trimmed, cut at 120, used **verbatim** as `external_course_id`, name and
  code — no hash, a hash hides nothing and makes DB repair harder.
  `external_id` = UID verbatim.
- **`horizon_days` is computed over the raw union of all fetched events,
  before any drop**, otherwise a student whose only far-out item is a dropped
  event gets a shortened removal window.
- **Site events, by two signals, erring toward keeping data:** a `CATEGORIES`
  value absent from `courses` is dropped only if it also matches a
  `calendar/siteevents` string from the bundled language table. A value absent
  from `courses` that matches no known string is **kept as a course** (that is
  C6, a group-only course) and flagged `unmatched_category` in telemetry so the
  language is added. Any event with no `CATEGORIES` is dropped (personal
  reminders, user overrides, category events). *(Decision 8.)*
- **Override rule:** for every base UID present in `courses` but absent from
  `all`, find in `all` the event whose stripped `SUMMARY` is
  `${baseName} - Override` (no `CATEGORIES`) or `${baseName} - <anything>` with
  the same `CATEGORIES`; take its `DTSTART` as the base UID's due; count
  `overrides_applied`; if nothing matches keep the base date — **never drop the
  task, never import the override event as its own task** (its UID churns when
  the override is lifted).
- **Title** = `SUMMARY` with the suffix stripped, longest match first, cut at
  240. **Skip** events whose suffix marks an opening or a grading deadline.
  **Pre-3.3 quiz rule:** when an event has a duration and no recognised suffix,
  its due is `DTEND`.
- **Language-agnostic pairing fallback:** two events in the same course with
  the same base name and the same `LAST-MODIFIED` minute, one earlier than the
  other, are the open/close of one activity — keep the later one.
- **Type:** `quiz` when the suffix was a close and the name matches
  `/\b(quiz|test|exam)\b/i`; `exam` by `classify`'s exam words; `other` for
  "should be completed"; else `classify(title, uid)`.
- Due from `dateParts(DTSTART)`; `external_updated_at` from `LAST-MODIFIED`
  else `DTSTAMP`; `url` = `${wwwroot}/calendar/view.php?view=day&time=<epoch>`
  (the day view is a real page, so *Open in Moodle* lights up); description via
  `truncateDescription(…, 'Moodle')`; dedupe on `${courseKey}:${uid}`;
  per-course counts and spans exactly as Canvas; bound at 5,000 items.

**1.6 `fetchMoodleCalendar`.** Normalise; `assertPublicCalendarHost`; fetch
**`courses/custom` and `all/custom` first**, in parallel with
`Promise.allSettled`; **request the `recentupcoming` pair only when the custom
horizon is under 60 days** — four requests per student per hourly sync is four
times what Canvas costs a school and exactly what a WAF rate rule catches
*(decision 13)*. Each request: origin-pinned redirects (max 3),
`AbortSignal.timeout(20_000)`, `Accept: text/calendar, text/plain;q=0.9`, the
user agent per decision 1, 5 MB caps. Union each pair by UID.

**Classify each body by its text, before parsing, and never by status code or
content type:**

| body | code | effect |
|---|---|---|
| contains `BEGIN:VCALENDAR` | — | parse |
| `/^\s*Invalid authentication/i` | `moodle_feed_expired` (status 401) | credentials_required, Vault purged, reconnect offered |
| `/^\s*no export/i` | `moodle_export_disabled` (status 401) | same, plus `last_error` names the cause |
| HTML with no `VCALENDAR`, or any HTTP 4xx, or a `cf-mitigated` header, or a "Just a moment" title | `moodle_feed_blocked` | **credential kept**, backoff 1→24 h, honest copy, counted in 5.6 |
| 429 / 5xx | the existing throttle shape | backoff |
| cross-origin redirect | `moodle_feed_redirected` | refuse, hint to copy from the canonical site |
| custom body over the cap | keep `recentupcoming`, pin the canonical URL preset to it | never rewrite back |

Return `{ courses, assignments, horizon_days, complete, recentupcomingOk }`.

## 9. What it cannot do

- List a course with no dated work, an unreleased course, or a course with
  only undated assignments — identical to Canvas today.
- Honour an extension on anything but an assignment. Only `mod_assign` emits an
  extension event; no other module has the concept.
- Points, grades, submission or completion state. The feed carries none.
- Per-item deep links. The feed has no URL; *Open in Moodle* opens the day.
- Stable course identity. The shortname is the only key; 3.5 mitigates a
  rename by event ids but cannot anchor a course that changed both name and
  every event.
- Survive a password change for a non-SSO student, or a salt rotation for
  anyone.
- Work where export is switched off, or read past an admin-narrowed
  look-ahead beyond the 60-day floor.
- Read opening dates, grading deadlines or undated work.
- Know the module type; it is inferred from the suffix and keywords.
- Reconcile deletions outside the window the feed showed, or delete anything
  the student touched.
- Use the browser sign-in road (§12).
- Confirm every school's Moodle before the browser opens.
- Provide a school directory on day one.

## 12. Appendix B — The parked sign-in road

Recorded so it is never re-derived.

**Why it is parked**, from `MOODLE_405_STABLE`:
`admin/tool/mobile/launch.php:70-76` throws `pluginnotenabledorconfigured`
before login unless the student just logged in, OAuth2 auth is enabled, or
`typeoflogin` is browser (2) or embedded (3); the site default is 1.
Lines 118-124 replace the requested `urlscheme` with `tool_mobile/forcedurlscheme`,
whose default `'moodlemobile'` (since 3.8; sites installed on ≤3.7 and upgraded
keep an empty value) sends the token to the official app and is not exposed by
`tool_mobile_get_public_config`. The return (`<scheme>://token=<base64>`) can
never reach `app.semoraai.com`. Registering `moodlemobile://` ourselves is
non-deterministic on iOS when the official app is installed.

**Unpark condition:** the 5.6 probe table shows many `typeoflogin` 2/3 hosts,
**and** an administrator at a real school confirms a blank `forcedurlscheme`,
**and** the owner's explicit yes.

**If it is ever built:** generate a 32-byte random passport; persist
`{ wwwroot exactly as the probe returned it (no trailing slash — Moodle computes
md5($CFG->wwwroot . passport)), passport, createdAt }` in `lmsSetupProgress`
with a 15-minute TTL; open `WebBrowser.openAuthSessionAsync(`${launchurl}?service=moodle_mobile_app&passport=${passport}&urlscheme=semora`
(+ `&oauthsso=${issuerId}` only when `typeoflogin=1` and exactly one identity
provider was returned), 'semora://token=')`; on return match the **raw** URL
with `/^semora:\/\/token=([A-Za-z0-9+\/=]{16,2048})$/` in `app/+native-intent.tsx`
and in a branch **above** the auth-callback handling in `app/_layout.tsx` —
never through `Linking.parse` or expo-router's path (base64 `/` and `+` are
mangled); base64-decode, split on `:::`, verify `siteid === md5(persistedWwwroot
+ passport)` with a pure-JS md5, reject on mismatch or TTL; single-use claim
modelled on `claimAuthCode` for Android's double delivery; discard the
private token; send the token only to `enable_background`; never log or track
it; never let the URL fall through to the auth-callback branch, which signs the
user out. The token grants the whole `moodle_mobile_app` service including
write functions, so the server exposes only the read functions it needs.
**Identity for that lane:** `core_calendar_get_calendar_events` (no action
filter) or `core_course_get_contents` `dates[]` as the complete source — **not**
`core_calendar_get_action_events_by_timesort`, whose events vanish once the
student has submitted, so a lane built on it would read completed work as
removed; `external_id` = the same calendar event id the feed UID carries,
`external_course_id` = shortname, so a feed connection upgrades in place. On
Moodle ≥3.10 `core_calendar_get_calendar_export_token` can mint the feed URL
and store it as the secondary credential so deadlines never go dark when the
token expires (`tokenduration` default 12 weeks).

|---|---|---|

The honest "compatible" form is the long-standing well-behaved-bot convention:
it names Semora, links to a page an administrator can read, and impersonates
nobody. It passes everywhere the Safari string does. There was no honesty
versus reach trade-off to make — only a badly shaped string. Applied.

### A real bug, found only with live data

A calendar event created on a live Moodle 5.0 and named `Tom & Jerry essay`
comes back as:

```
SUMMARY:Tom &amp\; Jerry essay
```

Moodle runs every name through `format_string()`, which HTML-escapes it, and
the iCal serialiser then escapes the resulting semicolon. `decodeIcsText`
undoes the second layer; the first survived, so a student would have read
`Tom &amp; Jerry essay` as their task title.

The same applies to `CATEGORIES`, and that is worse: the shortname **is** the
course key, so a course genuinely called "Class & Conflict" would have become a
Semora course permanently named `Class &amp; Conflict`. One of the 19 courses
on the demo account is exactly that shape.

Fixed with `decodeMoodleEntities`, applied to SUMMARY, DESCRIPTION and
CATEGORIES, tested against the captured feed. `&amp;` is decoded last so an
escaped entity survives as text.

### Live confirmation of the honest limit

The demo student is enrolled in **19 courses**. Two have dated work in the next
year. The rest would not appear in Semora at all until an instructor sets a
date — which is exactly what §3 says and what the review screen now tells the
student in their own words.

### Free, and admin-free: verified against production

`lms_access_allowed(uid)` is `is_pro(uid) OR promo_active('canvas_free') OR
grandfathered`. It names no provider — `canvas_free` is a promo key, not a
filter — so Moodle is already free on precisely the same terms as Canvas.
Checked live: the promo is active and all 532 accounts created in the last 30
days pass the gate. No code change was needed.

Admin-free is structural: the calendar export authenticates on a token the
student's own browser mints, needs no capability, and is on by default. The
web-service token that *does* need an administrator is now behind one small
link instead of being the only door.

### Three blind spots closed

Auditing the journey against the events found three places a student could
stall with nothing recorded:

| new event | the question it answers |
|---|---|
| `lms_provider_tapped` | did they even choose Moodle? The first step was invisible |
| `lms_setup_returned` | **did they come back from the browser?** A student who left and never returned looked identical to one who returned and gave up |
| `lms_setup_paste_rejected` | what did they paste when it was wrong? Fires while they are still looking at the field, so it catches the ones who read the hint and quit without submitting |

That last pair is the difference between "nobody can find the link" and
"everybody finds the wrong page", which need opposite fixes.
